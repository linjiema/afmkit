## Goals (in priority order)

1. **Interactive peak review** — the missing piece that makes afmkit
   usable for real experiments. Researchers will not trust automatic
   peak detection until they can accept / reject / re-fit each peak
   by hand.
2. **Plot overlay in the TUI** — once you can pick peaks interactively,
   you need to *see* them on the force–extension curve with the WLC fit
   overlaid. Visual closure.
3. **FJC model + pluggy entry-point demo** — round out the polymer
   model surface (WLC, eWLC, FJC) and exercise the plugin system we
   built in v0.1.
4. **Documentation site + GitHub Pages** — afmkit is a research tool
   that other labs will look at. mkdocs + Pages makes it findable.

## Four parallel pieces

### Piece 1 — `analysis/peak_review.py` (Coder N)

**New file:** `src/afmkit/analysis/peak_review.py`

Pure data + state machine. No TUI dependency. Public surface:

```python
@dataclass(frozen=True)
class ReviewedPeak:
    """A Peak tagged with manual review state."""

    peak: Peak  # the original Peak
    accepted: bool = True
    manual_force: float | None = None  # user-override force (pN)
    note: str = ""


class PeakReviewer:
    """State machine over a list of peaks."""

    def __init__(self, peaks: list[Peak], curve: ForceCurve) -> None: ...
    def accept(self, idx: int) -> None: ...
    def reject(self, idx: int) -> None: ...
    def override(self, idx: int, manual_force: float) -> None: ...
    def re_fit(
        self, idx: int, engine: LmfitEngine, x_range: tuple[float, float]
    ) -> None: ...
    @property
    def accepted(self) -> list[ReviewedPeak]: ...
    @property
    def rejected(self) -> list[ReviewedPeak]: ...
    def to_dict(self) -> list[dict[str, Any]]: ...  # for CSV export
    def __len__(self) -> int: ...
    def __iter__(self) -> Iterator[ReviewedPeak]: ...
```

**Tests:** `tests/unit/test_peak_review.py`, 12-15 cases. All state
transitions + re-fit round-trip + CSV dict export.

**Scope:** ONLY this file + its test. Do **NOT** touch the TUI —
that's piece 2's Lead-integrated wiring.

### Piece 2 — `presentation/gui/plot.py` (Coder O)

**New file:** `src/afmkit/presentation/gui/plot.py`

A Textual widget that renders a force–extension curve with optional
peaks + WLC fit overlay, using the matplotlib Agg backend. Public
surface:

```python
class ForceExtensionPlot(textual.widget.Widget):
    """A static matplotlib plot of a force–extension curve."""

    def render_curve(
        self,
        curve: ForceCurve,
        peaks: list[Peak] | None = None,
        fit: FitResult | None = None,
        x_range: tuple[float, float] | None = None,
    ) -> None:
        """Render a new (curve, peaks, fit) triplet into the widget.
        Uses matplotlib's Agg backend to draw into a Pillow image,
        then renders the image as the widget's text via rich's
        Image protocol."""

    def clear(self) -> None: ...
```

The widget should not crash on empty data, NaN data, or a curve with
no detectable peaks. It should also degrade gracefully if matplotlib
is not installed (raise ImportError with an install hint from
`action_render`).

**Tests:** `tests/unit/test_plot.py`, 5-8 cases. Headless rendering
to a Pillow image, no actual terminal output. Verify the widget can
be constructed, `render_curve()` produces a non-empty Pillow image
of the right size, and clearing / re-rendering works.

**Scope:** ONLY this file + its test. Do **NOT** touch the TUI
`app.py` — Lead integrates it after piece 1 lands.

### Piece 3 — `models/fjc.py` + pluggy entry-point demo (Coder P)

**New file:** `src/afmkit/models/fjc.py`

`FJCModel` — the Freely Jointed Chain in the Odijk–Wu interpretation
(F = (kB*T/b) · [L(1-x/L)^(-1) − 1/4·(1−x/L)^(-2) − 1/4 + x/L], or
the simpler classical form
F = (kB*T/b) · [coth(Fb/kBT) − kBT/(Fb) − x/L], 3 parameters: b
(Kuhn length, nm), Lc (contour length, nm), k0 (stretch modulus
optional, pN)).

Pick the **classical FJC** (no stretch) as the v0.3 default. It's
the one most papers compare against and matches the behavior
researchers expect from Igor's built-in. Document the choice in
the module docstring.

**Modified file:** `src/afmkit/models/__init__.py` — add the
`"fjc"` registry entry, same as the eWLC pattern.

**Modified file:** `pyproject.toml` — add an entry-point block to
demonstrate pluggy discovery:

```toml
[project.entry-points."afmkit.models"]
fjc = "afmkit.models.fjc:FJCModel"
```

(pluggy auto-discovers models registered this way. This is the
canonical pattern; the in-tree `MODEL_REGISTRY` and the entry-point
mechanism are now both exercised.)

**Tests:** `tests/unit/test_fjc.py`, 10-12 cases. Numerical
correctness (F = ∞ at x = Lc, F → ∞ as x → Lc), Kuhn-length limit
to the freely-jointed limit at b → 0, registry membership, pluggy
discovery (call `pluggy.load_setuptools_entrypoints("afmkit")` and
verify `fjc` is one of the loaded hookimpls).

**Scope:** ONLY the model file, the registry entry, the entry-point
config, and the test.

## Risk register

| Risk | Mitigation |
|---|---|
| 4 Coder agents run in parallel, 1-2 hit the 5h token cap | Tight file scope per Coder; Lead is ready to take over a stuck agent's WIP. Same pattern as v0.2. |
| Coder O's matplotlib widget pulls in a heavy dep | Add matplotlib to `[plot]` extra (already there in pyproject but verify). The widget must be import-gated so a minimal install without `[plot]` doesn't break `afmkit gui`. |
| Coder P's entry-point pattern conflicts with the existing in-tree `MODEL_REGISTRY` | Test explicitly that the entry-point *adds* to the registry, not replaces it. The pluggy `afmkit.models` hookspec is unused for v0.3 — we only register an entry-point and verify it loads. |
| Coder Q's docs build fails on missing files | `mkdocs build --strict` is the contract; iterate until it passes. |

## Token budget per Coder

- 30 minutes of work each
- Do **NOT** iterate on test suites or run ruff format repeatedly
- One pre-commit verification, one post-commit verification, that's it
- If stuck, **stop and commit** what you have (Lead finishes)
